# BrawlMeta — Claude handoff

Brawl Stars stats + automated-tournament site. Live at **https://brawl-meta.vercel.app**.
Stack: Vite + React (no TS) · Vercel serverless functions (`api/`) · Supabase Postgres · Python scrapers on GitHub Actions.

⚠️ **This repo is PUBLIC.** Never commit secrets, key values, or tokens into any file — including this one. Document where a secret lives, never what it is.

## Core principles (non-negotiable)

1. **Players NEVER pay.** Monetization is premium subscriptions + organizer fees only. No player-side charges, ever.
2. **Premium is enforced server-side** (checked in `api/` against the DB), never trusted from the client.
3. **Display names are permanent and globally unique** (case-insensitive). Once set, locked. Signup autofills it; profile shows 🔒.
4. **Player tags are globally unique and freeze after the first tournament played** (anti account-selling/impersonation). Future: verify tag ownership via the Supercell API before real-money prizes.
5. **`ranked_matches` uses owner-authorized windowed retention** (2026-07-20): the Masters bracket is FIFO-capped at 1.5M rows by `collected_at` via the `prune_ranked_matches` RPC, called only by the masters scraper after each push. NEVER bulk-delete outside this mechanism, never manually; schema changes stay additive, verified migrations only.
   - **`collected_at` is the "when was this collected" column and it already exists on every row** — this is the answer to "how do we know which games are oldest". `prune_ranked_matches` orders by `collected_at ASC` and deletes oldest-first, so no batch/date column needs adding. Rows that predate the column carry the migration timestamp (533,421 of them share `2026-07-20 13:48:15+00`), which is exactly the "mark everything existing with one timestamp" backfill.
   - **Logged exception (2026-07-22, owner-instructed):** when a map leaves the ranked rotation its rows become dead weight in the capped window, so Rustic Arcade's 7,144 `ranked_matches` rows + 103 `BrawlerStats` rows were deleted by hand. Order matters and is the reusable recipe: **remove the map from `RANKED_MAPS` in `scrapers/common.py` and PUSH first**, confirm the in-flight scrape has finished (`max(collected_at)` stops advancing), *then* delete — otherwise the running job re-inserts everything. The `maps` lookup row is deliberately left in place so the id survives if the map ever rotates back. Still requires explicit owner instruction each time. **Rustic Arcade rotated BACK IN and was re-added on 2026-08-24 (owner-instructed)** — the preserved lookup row did its job and the id survived, so collection resumed cleanly.
   - **Logged exception (2026-08-17, owner-instructed):** patch `67.306` closed long ago and its rows were dead weight in the capped window, so all of them were deleted by hand — 28,314 `ranked_matches` (26,220 diamond + 2,094 masters) and 4,136 `BrawlerStats`; `brawler_intelligence` had none. Safe without the stop-the-scrape dance the Rustic Arcade recipe needs, because `CLOSED_PATCHES = {"67.306"}` already makes `fetch_player_battles` drop those matches at parse time — nothing can re-insert them. Verified 68.250 untouched at 1,668,098 rows before and after. The `patches` lookup row is left in place, same reasoning as the `maps` row.
   - **Counting rule this exposed:** anything compared against `MASTERS_BASELINE` must count the bracket across **all patches**, because `prune_ranked_matches` caps the window that way. `get_stored_match_count` defaults to `CURRENT_PATCH`, so pass `patch_name=None` for window comparisons — see the scraper-throttle entry under Hard-won pitfalls.
6. **`SUPABASE_KEY` used by scrapers is the service-role key** — GitHub Actions secrets only, never in the browser bundle. The frontend uses the anon key (`VITE_SUPABASE_KEY`).
7. New tables get RLS enabled + a `"Public read access"` SELECT policy for `anon, authenticated`; writes happen via service role (bypasses RLS) or SECURITY DEFINER RPCs with `auth.uid()` guards.

## Architecture map

- **`src/`** — React app. `appCore.js` (supabase client, shared hooks: `useMapMatches` reads the `Matches` VIEW), `App.jsx` (tabs: tier list / leaderboards / draft), `DraftAssistant.jsx`, `TournamentPages.jsx`, `SiteHeader.jsx`, `AuthModal.jsx`.
- **`src/data/`** — `draft_logic_config.json` (**single source of truth** for the Intelligence Engine: Bobby's 7 draft classes, counter matrix, mode tempo, coefficients, plus `mapProfiles` (per-map openness/bush geometry), `brawlerAttributes` (range/attackType/spawner/bushSynergy) and `attributeRules` (geometry & spawner interaction rules, dampened when live map data exists), plus the pro-source layer `mapRules` (per-map requirements/biases/ban advice from SpenLC breakdowns), `brawlerBias` (mode-scoped tier corrections for balance changes the aggregate hasn't priced in), `brawlerCounters` (named brawler-vs-brawler edges) and `firstPickCaution` — read by BOTH the browser engine and Python), `draftEngine.js` (5-pass draft advisor + win split), `draftMeta.js` (per-brawler blind-pick safety), `brawlerMeta.json`, `bracket.js` (tournament math), `verifyLogic.js`.
- **`api/`** — Vercel serverless (ESM). Tournament flow: `generate-bracket`, `tournament` RPC callers, `report-result` (OCR fast-path), `verify-match` (battle-log check), `report-dodge`, `set-lobby-invite`, `bracket-state` (lazy sweeps, `advanceAndMaybeFinish` completes tournaments + credits wallets), `declare-winner`, `reset-match`, `player` (live player card lookup). Shared: `api/_lib/db.js`, `api/_lib/ocr.js` (Claude Haiku vision, model `claude-haiku-4-5-20251001`), `api/_lib/proxyFetch.js`.
  - **These run only on deployed Vercel** — NOT under local `npm run dev`.
- **`scrapers/`** — Python package, one module per source: `player_tracker.py` (per-player battlelog poller → `player_matches`; adaptive interval, see below), `masters.py` (spider, 1.5M baseline → 50k steady, then FIFO window prune at 1.5M; top-200 seeding from brawlytix.com — plain server-rendered HTML, browser UA only, confirmed 2026-07-20 — with brawlace as a Cloudflare-JS-gated secondary source via `cloudscraper`+proxy, and the spider self-seeds `masters_players` with depth-1-from-verified-only discoveries, replaced each run to bound drift, anchored by the 5 hardcoded pros so both sources being down never stops rotation), `diamond_mythic.py` (gated on Masters baseline), `leaderboard.py` (top-200 + event rotation), `meta_weights.py` (syncs `brawler_classes` from the config, refreshes `brawler_intelligence` + pair RPCs), `common.py` (shared spider/insert pipeline + `prune_bracket`; dedupe is DB-side via `on_conflict=match_hash&ignore-duplicates`).
- **`.github/workflows/`** — one workflow per scraper: `track-players.yml` (02:20/10:20/14:20/20:20 UTC — slots chosen against the masters run's real ~70-85 min duration, not just its start minute), `scrape-leaderboard.yml` (05/11/17/23 UTC), `scrape-masters.yml` (00/06/12/18 UTC — 4×/day, one hour after each leaderboard run), `scrape-diamond-mythic.yml` (07:30 UTC), `refresh-intelligence.yml` (08:30 UTC safety net). All have `workflow_dispatch`.
  - **Masters throughput is bounded by graph saturation, not rate limits.** A single run exhausts the 2-hop neighbourhood of its seeds at ~33k players / ~30k unique matches and logs "ran out of players" well under `MAX_PLAYERS_PER_BRACKET`. More seeds barely helps (the top-200 all queue against each other, so their neighbourhoods overlap); raising `SPIDER_DEPTH` past 2 would help but that cap is exactly what enforces rank purity. The lever that works is **frequency** — the same players generate new games between runs. Hence 4×/day while filling the 1.5M baseline.
  - **`parse_battle(match, player_tag, bracket)` in `common.py` is the single source of truth for what counts as a collectable Ranked match** — shared by the spider and the tracker so they can never drift. It returns `(frontier_tags, record)`. The split is load-bearing: the spider queues those tags even when the battle is then rejected (closed patch, unlisted map), and folding them into the record would silently shrink the spider's reach. `record` carries both the absolute view (`winners`/`losers`, for the composition hash) and the view relative to `player_tag` (`team_*`/`enemy_*`/`result`). **The API's `result` is relative to whoever's battlelog you read** — the same game is `victory` in one log and `defeat` in another — which is why both views exist.
  - Matches collected is always well below players processed: each match sits in up to 6 battlelogs and is deduped via `seen_hashes`, battlelogs are all-modes (trophy/showdown/friendlies are filtered out), and the map + patch allowlists drop more.

## Database (Supabase Postgres)

Normalized match storage (2026-07-16; DB went 149→68 MB):
- **`ranked_matches`** — uuid PK = the scraper's md5 dedupe hash; smallint FKs `map_id/bracket_id/patch_id/w1-w3/l1-l3`; `collected_at` (added 2026-07-20, pre-existing rows carry the migration timestamp) drives the FIFO window + recency stats. Indexes `(patch_id, map_id)`, `(bracket_id, collected_at)`.
- **`ranked_matches.times_seen`** (added 2026-08-27) — how many ROUNDS collapsed into that composition row. **A Ranked series is one draft on ONE map, up to 3 rounds** (measured: 16,349 series, 100% same map, avg 2.32 rounds over ~167s). Every round of a 2-0 hashes identically, so the extra rounds were silently dropped — **45.5% of all rounds played**. Worse, a **2-1 stored one row each direction and read as a flat 50/50**, and 34.5% of series are 2-1, which compressed every comp-level win rate toward the middle. The counter is per direction, so a 2-1 is `A>B times_seen=2` + `B>A times_seen=1` = 67/33. **Repetition never adds rows** — a later 2-0 between the same comps on the same map takes the same row from 2 to 4. Storing every round instead was rejected deliberately: it costs 1.73x the rows for the same games, which inside the fixed 1.5M window is **42% fewer distinct compositions** (~13 days of coverage down to ~7.5), and it re-introduces pseudo-replication because rounds of one series share players, skill, map and draft. **`times_seen` is stored but NOT yet weighted into any aggregate** — how to weight it (1, sqrt(n), or n) should come from the measured distribution, not a guess. Rows predating the column default to 1.
- **Inserts go through the `upsert_ranked_matches(rows jsonb)` RPC, not a plain PostgREST upsert.** PostgREST can only ignore or overwrite on conflict and `times_seen` has to ADD, since a composition re-seen on a later run was genuinely played again. It returns the count of genuinely NEW rows (via `xmax = 0`). **`collected_at` is deliberately not touched on conflict** — bumping it would let popular comps refresh their own age forever and never reach the front of the FIFO prune, slowly filling the window with whatever recurs most. EXECUTE is granted to `service_role` only (revoked from PUBLIC as well as anon/authenticated — the PUBLIC grant is the one that bites).
- Lookups: **`brawlers`**, **`maps`** (carries `mode`; map→mode is 1:1), **`patches`**, **`rank_brackets`**, **`brawler_classes`** (draft class per brawler, synced from config).
- **`Matches` is a VIEW** (security_invoker) over `ranked_matches` with the legacy shape (`map,mode,rank_bracket,patch,winners,losers,match_hash`) so the frontend never changed. **It is read-only — INSERT into `ranked_matches`, never the view.**
- **`BrawlerStats`** — tier-list aggregates; rebuilt by RPC `aggregate_brawler_stats(target_patch)`.
- **`brawler_intelligence`** — per patch+bracket+brawler: Bayesian `true_win_rate`, flags (`popularity_trap`/`broken`/`inflation_bias`), `vs_class` jsonb (empirical WR vs each enemy class), `vs_brawler` jsonb (WR vs each specific enemy brawler, ≥`pairMinPicks` pairs) and `with_brawler` jsonb (duo WR with each specific teammate). Rebuilt by RPC `refresh_brawler_intelligence(target_patch, coeff)`; the pair columns by `refresh_brawler_pairs(target_patch, target_bracket, coeff, recent_limit)` called once per bracket (inlining them into the main RPC blew the statement budget on 470k+ matches — keep them split). **The pair RPC is the first thing to break as the window grows**: it unrolls every match into 30 pair-rows, so at 1.11M Masters rows (2026-07-28) it hit ~33M rows, exceeded the PostgREST gateway timeout, failed on every scrape and left `vs_brawler`/`with_brawler` as `{}` — which silently empties the brawler guide's Match-ups section. It now bounds itself to the most recent `recent_limit` matches (default 600k, ~24s) via the `(bracket_id, collected_at)` index, so cost stays flat as the window fills to 1.5M; lower that default if it regresses. Symptom to watch for: Match-ups vanishing from a guide page means these columns are empty, not a UI bug. Coeff comes from the config JSON. `pick_rate` here = share of matches (0–100), NOT share of total picks.
- **Player history (added 2026-08-24, Phase 1 of the player-stat plan; see `docs/brawlify-analysis/`):**
  - **`tracked_players`** — poll registry. `tier` (0 claimed / 1 tournament / 2 looked-up / 3 seeded) sets a floor on `poll_interval_mins`; the interval halves when a poll returns ≥20 new battles (we're being outrun by the ~25-battle buffer) and backs off when it returns few or none, deactivating at 7 days. `seed_bracket` labels a player's games by the list they were seeded from — **the API exposes no per-match rank tier**, so this is the same proximity approximation the spider makes, and it is NULL rather than guessed for unknown players. Seeded with 1,432 tags from `masters_players` + `top_200_leaderboard` + `diamond_mythic_players`.
  - **`player_matches`** — one row per (battle, tracked player), denormalized so a profile page is one index scan. **`match_key` is an IDENTITY hash (battleTime + all six tags), NOT `make_hash`'s composition hash**, so the two tables are deliberately not joinable: a player's history needs one row per round actually played, while `ranked_matches` merges rounds of one series (see the collision measurement below).
  - **`player_snapshots`** — created but **deliberately unwritten** until the profile UI exists; trophy curves need a second `/players` call per player, doubling every run's cost against the shared key for a feature nothing reads.
  - **`prune_player_matches(per_player_cap, max_age_days, inactive_days)`** — retention from day one. **Separate from `prune_ranked_matches` and never called by it.** EXECUTE is revoked from `anon`/`authenticated` — a SECURITY DEFINER function that deletes rows must not be reachable from the browser.
- **`map_class_weights`** (added 2026-08-29) — measured per-map class fit in WIN-RATE POINTS, replacing the hand-authored `modes[].classWeights`. `lift_pts` = how much a class over/under-performs on that map relative to its own brawlers' global rates (so brawler strength is removed), shrunk toward 0 by sample. Rebuilt daily by `refresh_map_class_weights(target_patch)` from `meta_weights.py`, so it tracks the meta instead of rotting; service_role only; RLS + public read. **Why it exists: the authored weights were never checked and were actively HURTING.** Held out over 23,772 pick decisions they cost **−0.0041 AUC at shipped strength and −0.0083 at 1.5×** — a clean monotone slide, more damage than every improvement of that week combined. The cause is that they MULTIPLIED a 50–90 point score, so `CONTROL ×1.15` in gemGrab was worth ~+11 points where the effect measures **−0.31**; individual cells were also plainly inverted (heist gave TANK the mode's biggest bonus at ×1.15 while tanks measure **−3.08** there, a 9-sigma error; brawl ball gave THROWER the biggest penalty at ×0.75 while throwers are the mode's best class at **+1.38**). Overall the authored table scored r = 0.31, 24/41 signs. **The replacement is ADDITIVE and its own effect is NEUTRAL (−0.0000 ± 0.0013) — the gain is from removing a harmful term, not adding a predictive one**, because class-level map fit is largely subsumed by the brawler's own per-map win rate that the score already carries. Per-map beat per-mode on validation (0.5505 vs 0.5501); neither cleared its error bar on test. `modes[].classWeights` survives ONLY as the fallback for a map with no rows, and `modes[].tempo` is still load-bearing for the thrower and anti-tank rules — do not delete it.
- **`map_pair_edges`** (added 2026-08-30) — head-to-head for a brawler pair **on a specific map**, the per-map layer `mapPairs` was always named for. **The largest single gain the calibration pass has produced: +0.0043 ± 0.0029 AUC** on 23,772 held-out pick decisions, beating the +0.0032 from refitting every recommender weight at once. The engine shrinks each entry toward the patch-wide `vs_brawler` rate by its own sample at `mapPairs.mapShrinkPriorGames` (50, deliberately below the patch-wide 135 — validation preferred the smallest prior tried and the curve is monotone, so this layer wants MORE weight). Only pairs above the RPC floor are stored: of 169,191 per-map pairings **just 18.7% reach 30 games and 2.6% reach 200**, and everything below falls straight through to the patch-wide rate, which is what shrinkage would have done anyway. ~79k rows Masters / ~92k Diamond, max ~3.8k per map. Rebuilt daily by `refresh_map_pair_edges(target_patch, target_bracket)` from `meta_weights.py`; bounded by `recent_limit` (600k) for the same reason `refresh_brawler_pairs` is, since it unrolls each match into 9 cross-team pair rows. **Antisymmetry survives** — both directions are stored, so `mapWR(a,b) = 100 − mapWR(b,a)` and the blend weight is identical either way, which `computeWinSplit`'s differential depends on.
- Tournament tables: `Tournaments`, `Registrations`, `TournamentMatches`, `TournamentFeedback`, `Verifications`, `UserWallets`, `Profiles`.
- Feeds: `SiteFeed` (raw payload relays), `top_200_leaderboard`, `masters_players` (brawlace top-100), `diamond_mythic_players` (curated seeds).
- `brawler_intelligence` also carries `recent_picks/recent_wins/recent_win_rate` (last `recency.windowDays` days by `collected_at`); the engine blends recent WR at `recency.recentWeight` over the patch aggregate when the recent sample ≥ `minRecentPicks`, and shows Trending up/down chips on ≥`trendDeltaPct` divergence — this is the mid-patch shadow-nerf defense; announced balance patches are handled by bumping `CURRENT_PATCH` (patches = balance epochs).
- `service_role` has an explicit `statement_timeout = 600s` (set 2026-07-20 — the heavy RPCs outgrew the cluster default at ~475k matches and every aggregation 57014'd). Frontend roles keep 3s/8s. **`authenticator` also carries `lock_timeout = 8s`** — that 8s, not the 600s, is what a queued RPC will wait for a lock before dying with 55P03.
- **Two non-obvious limits on the heavy RPCs, both learned the hard way on 2026-08-02:**
  1. **A 504 does not mean the statement failed.** PostgREST gives up at the gateway while Postgres keeps running to its 600s budget, so the work usually still lands — *and the transaction keeps holding its locks the whole time*. On 2026-08-02 `refresh_brawler_intelligence` 504'd, kept running, and blocked the two `refresh_brawler_pairs` calls that `meta_weights.py` fires straight afterwards; they hit `lock_timeout` and failed with 55P03. **Any RPC that rebuilds a table should compute into a TEMP table first and do the DELETE+INSERT swap last**, so the exclusive lock covers the row swap rather than the whole scan. `refresh_brawler_intelligence` is now written that way.
  2. **Temp/spill space is far smaller than the database.** The DB is ~221 MB, but a rewrite of the `vs` aggregate that did `DISTINCT (match_hash, brawler, class)` over ~29M rows died with 53100 `No space left on device` on `pgsql_tmp`. **Don't put a big sort or DISTINCT in these RPCs** — stream instead. The working `vs` formulation joins the 105-row `brawler_classes` three times (once per enemy slot) and dedupes the three results inline with `IS DISTINCT FROM`: no sort, constant memory. It replaced a per-side-row correlated `SELECT DISTINCT` that had become ~9.7M correlated subqueries and stopped finishing at all. Verified identical to the old output over 200k- and 300k-match slices (728 groups, 0 differing) and by fingerprint over the full table.
  - Current full-pipeline cost at 1.42M Masters rows: intelligence refresh **16s**, masters pairs **21s**, diamond pairs **7s**.
- RPC gotcha: when changing a tournament RPC's signature, **DROP the old overload first** — duplicate overloads break PostgREST ("could not choose best candidate function").
- Patch bookkeeping lives in `scrapers/common.py`: `CURRENT_PATCH`, `PATCH_START_TIMES`, `CLOSED_PATCHES`, `RANKED_MAPS` per patch. On a new patch, update these + add the map list.
- **Patch rollover — the runbook, written from doing 68.250 → 69.230 on 2026-09-01** (the September balance patch: 22 buffed, 14 nerfed, new Buffies for Poco/El Primo/Amber and Gus/Chuck/Shade).
  1. **It is urgent and it is one-way.** `ranked_matches` stores `collected_at` but **no `battle_time`**, so a new-patch game stamped with the old patch can never be identified afterwards — there is nothing left to re-derive it from. The boundary must land before the next scraper run, not after the meta is understood.
  2. **Date the boundary from our own data, not from the announcement.** Supercell's maintenance break means *no ranked match exists* across it, so every candidate timestamp inside the dead window is equivalent — which makes the choice exact rather than approximate. Find the window with `max(battle_time)` in `player_matches` plus `tracked_players.last_polled_at`: for 69.230 the newest battle anywhere was `2026-08-31 23:56:51+00` while 66 accounts were polled as late as `07:54+00` with nothing new, so the game was down across that whole span. Pick the LATER end of the window (69.230 → `06:00 UTC`, matching the APK's 06:08 upload): spilling a few new games into a 2.1M-row patch is invisible, spilling old-balance games into a patch starting from zero poisons the first tier list anyone sees.
  3. **`RANKED_MAPS` needs a key for the new patch or the map filter turns OFF.** `parse_battle` does `allowed_maps = RANKED_MAPS.get(match_patch)` and skips the check when that is `None`. Bumping `CURRENT_PATCH` without adding a key does not tighten the allowlist, it removes it — every themed reskin and event map starts landing in `ranked_matches`, disguised as a great collection day. Copy the previous patch's set (`RANKED_MAPS["69.230"] = set(RANKED_MAPS["68.250"])`); `map_pool.py` unions the live rotation on top anyway.
  4. **The scraper and frontend `CURRENT_PATCH` are staged, not synced.** `scrapers/common.py` must move immediately (labelling); `src/appCore.js` must NOT (reading), because the new patch has no aggregates and pointing the app at it empties the tier list, map pages and draft intelligence in one commit. Both `aggregate_brawler_stats` and `refresh_brawler_intelligence` `DELETE ... WHERE patch = target_patch`, so the old patch stays intact underneath and the flip is reversible. Flip the frontend once the new patch is thick enough to aggregate honestly, and grep for hardcoded patch literals first — `BrawlerGuidePage.jsx` had `.eq("patch", "68.250")` written out, which would have left one section serving the old patch beside current numbers.
  5. Do **not** add the new patch to `LEGACY_HASH_PATCHES` (that re-arms the rollover data-loss bug), and do **not** put the old patch in `CLOSED_PATCHES` yet — battlelogs keep returning pre-update games for a day or two and closing it drops them at parse time.
  6. Nothing needs doing in the DB by hand: `LookupCache._ensure` creates the `patches` row, and any new brawler's `brawlers` row, on first insert.
  7. **Do NOT try to collect harder by running the spider more often — this was built, measured and removed (2026-09-01 to 09-05).** A "launch burst" made 3 spider passes per masters slot, 40 min apart, on the reasoning recorded elsewhere in this file that *frequency* is the lever because the same players keep playing between runs. Measured on rounds/day — the throughput number that, unlike new rows, does not fall as the composition space fills — it did **nothing**: 256k / 230k / 212k on the three days before, 251k / 259k on the two full days with it, ~260k the day after it expired. The reasoning holds across a 6h gap and fails across a 40-minute one, because a battlelog has barely turned over; passes 2 and 3 spent a full API budget re-walking an unchanged neighbourhood. **The ceiling is request throughput against the single shared Supercell key**, which more passes cannot raise — they only steal budget from `track-players` and `scrape-diamond-mythic`. The one sub-finding worth keeping: extra passes must go INSIDE one process, never into extra cron slots, because `SEEN_IDENTITIES`/`PUSHED_COUNTS` are per-process — extra workflow runs start with both empty and inflate `times_seen` for games played once. If anyone retries this, run one slot with and one without on the same day, and judge on rounds/day.
  8. **The Masters window is FULL at its 1.5M cap, so every new row EVICTS an old one.** Collecting faster while the frontend still reads the old patch is deleting the data the site is serving — accelerate and flip together, or flip first.
  - **Never use the previous patch as a statistical prior for the new one, and this is measured.** It is the obvious way to fill a thin new patch and it is wrong exactly where it matters: a balance patch is the moment the old patch stops being valid, and the error is largest for the brawlers the patch changed — the ones people look up. On 68.250 → 69.230 a previous-patch prior showed El Primo 48.7% against a real 53.1%, Amber 55.6% vs 59.0%, Shade 54.5% vs 58.0%, and pulled the NERFED Nori UP from 45.0% to 48.6%. Shrink toward the brawler's own MODE rate **within the new patch** instead (`shrunkWinRate` in `appCore.js`, prior = `mapPriority.blendPriorGames`, shared with the engine so a map page and a suggestion card cannot disagree). Measured over 2,071 cells: under 60 games moves 13.7 pts (sd 16.55 → 10.22), over 500 games moves 1.07. **Any list sorted by win rate needs this** — sorting raw rates puts the noisiest cell on top by construction, which is how a 37-game LILY was ranked first on Hot Potato at 67.6%.
  - **Buffies need no config change.** They upgrade gadgets / star powers / hypercharge, none of which the engine models — `brawlerAttributes` encodes range/attackType/spawner/bushSynergy and `brawlerAbilities` encodes wall/bush mechanics. Resist hand-authoring `brawlerBias` entries for a balance patch: that block is empty for a measured reason (it double-counted the score base), and the 14-day `recency` window plus the new patch epoch is the mechanism actually built for this.
- **The ranked map rotation is AUTOMATIC — do not hand-maintain it.** `scrapers/map_pool.py` reads the live rotation from brawltime daily (04:40 UTC) into `ranked_map_pool`; scrapers call `refresh_dynamic_map_pool()` and treat it as an ADDITION to `RANKED_MAPS`, never a replacement. This exists because a map rotating in was invisible — a battle dropped by the allowlist looks exactly like a battle that never happened, so Spiraling Out was silently discarded until the owner spotted it by eye. The source 403s a GitHub Actions IP, so it retries through the Webshare proxy (same wall as brawlace). It refuses to act on a parse below 12 maps / 4 modes, and can only widen the allowlist — a wrong addition is prunable, a wrong removal silently bins real matches. **`RANKED_MAPS` in `common.py` is now only a FLOOR**, not the live list: it is what the allowlist degrades to if the source breaks, since an empty allowlist would let event reskins pollute the dataset. There is no obligation to sync it after a rotation. **The ranked rotation turns over every day or two, not per patch** — measured 2026-08-24, six of twenty maps swapped between two runs hours apart. `refresh_dynamic_map_pool()` therefore unions EVERY map ever seen in the pool, not just `in_rotation=true`: the allowlist answers "is this a real ranked map", not "is it live right now", and a battlelog still holds games from maps that rotated out this morning. `in_rotation` is metadata for display, never a collection filter.
- **`Safe Zone` and `Safe(r) Zone` are DIFFERENT heist maps** (owner-confirmed 2026-08-24, correcting an earlier note that said otherwise). Never merge them. `mapSlug()` gives `safezone` vs `saferzone` so the engine's config lookups already keep them apart. ## Engine invariant: the counter matrix is antisymmetric

**The matrix is MEASURED as of 2026-08-29 and its unit is WIN-RATE POINTS, not the old authored −2..+2 score.** Every cell is the sample-weighted mean head-to-head edge over all brawler pairs in those two classes across 250k Masters matches. Three things about it are load-bearing:

- **Solo strength must be removed with a FITTED coefficient, not an assumed one.** Solo win rate alone explains **64%** of head-to-head edge, so an unadjusted matrix mostly learns which classes hold strong brawlers — which `soloWR` already scores. Regressing raw edge on the solo-WR difference gives a slope of **1.004**; an earlier pass assumed 0.5, and the leftover half of every strength gap produced two confident, wrong findings: that Anti-Tank does *not* beat Tank, and that Ash/Bolt are a separate archetype needing their own class. Both dissolve at the fitted coefficient — **Ash and Bolt are ordinary tanks** (matchup residual +0.18 and −0.16) that happen to be strong. If you re-derive this matrix, fit the coefficient first.
- **Cells are pooled WITHIN maps and then shrunk toward zero by their own standard error.** Both matter. Two classes are drafted onto different maps, so a raw cross-tab confuses that selection with a matchup — Tank vs Thrower reads **+0.52 raw and −0.05 map-controlled**. Shrinkage (empirical Bayes; across 42 cells the observed sd is 0.86 pts of which 0.21 is noise) then stops a thin cell asserting what its sample cannot carry. The first pass had neither and shipped a +0.63 Tank-vs-Thrower edge that was pure map selection.
- **Bobby's triangle largely survived contact with the data** (r = 0.579 with the authored table): Anti-Tank does beat Tank (+1.06, not the claimed +2.00), Space Maker does dive backline (+2.06 vs Thrower, +1.12 vs Sniper), and Anti-Tank does lose to Thrower (−1.71). Both genuine corrections are in the **Tank row**: tanks were said to lose 1.5 to throwers — that is **not true and not reversed either, it is 0.00, a wash**, and it is the single largest false claim in the old table (it is what made the engine show Ash "Weak vs Barley"); and tanks were said to lose 1.0 to snipers when they in fact **beat** them (+0.60, which does clear its error bar).
- **The largest cell has an independent confirmation.** SPACE_MAKER vs THROWER (+2.06) reproduces as a clean monotone dose-response measured a completely different way: across 332,172 Masters games a thrower is **+2.89** win-rate points against a comp with no space maker, **−2.06** against one, **−4.73** against two and **−8.66** against three. The matrix term (−2.06 × `classCounter.adviceWeight` 2.0 per space maker) lands within a point of that per step, so the magnitude is already priced — **do not add a separate thrower penalty for enemy space makers or it double counts.** `counterLadder.throwerLastPick` reads the matrix to decide whether a counter is present, so that rule follows the data instead of a hand-listed class — **but a class check alone is not enough there, and that is the general lesson**: BOLT is the game's best thrower counter at **+12.27**, and he is a TANK, whose class cell against THROWER is −0.04. Shelly (Anti-Tank +5.71), Brock (Sniper +5.55), Ash (Tank +4.99) and Gray (Support +3.68) are the same — five of the fourteen strongest thrower counters are not space makers. **Any rule gated on the class matrix must also check the measured `vs_brawler` pairing**, at `mapPairs.chipEdgePts`, or it will wave through exactly the brawlers that matter most.
- **A class cell is not a duel.** It is a team-level outcome for comps containing those classes, and within-class spread dwarfs the class mean: against throwers, Bolt is **+5.79** and Buster **−5.19** around a class mean of zero. Never quote a class cell as advice about two specific brawlers — `vs_brawler` is where per-brawler truth lives.
- **A class matrix cannot add much, and this is now settled.** Held out over 23,772 real pick decisions, removing it *entirely* moves AUC by **−0.0008 ± 0.0010**; swapping authored values for measured ones moves **+0.0002 ± 0.0013**; 18 classes learned by co-clustering did no better. None clear their own error bar, because brawler-level `vs_brawler` already covers 93% of decisions. **It is kept because it explains picks, not because it ranks them** — it drives every Counters/Weak-vs chip and the `counterStack` rule. Don't re-litigate this with another clustering scheme; the ceiling is the coverage of `vs_brawler`, not the quality of the classes.
- Because the scale shrank (RMS 0.88 vs 1.21), two thresholds read against it moved with it: `classCounter.chipThreshold` 1.5 → 1.0 and `constraints.counterStack.hardCounterThreshold` 1.5 → 1.0. At 1.5 only two of 42 pairings could ever fire and both rules would have gone silently dead. **Any future rescale of the matrix must move these two with it.**


`counterMatrix[a][b] === -counterMatrix[b][a]` for every pair. Anything that scores BOTH sides and then takes the difference therefore counts each cross-team pairing **twice** — `computeWinSplit`'s differential is `blue.counter - red.counter = 2 × blue.counter`. That is why `winProbability.counterWeight` would be 0.6 rather than the intuitive 1.2 — though it is **0 today**, so the verdict path does not read the matrix at all and changing matrix values cannot disturb the fitted `logisticScale`. Fixed 2026-07-25: at 1.2, class theory could swing the differential ~26 points while the statistical term (a mean of true win rates) spans barely 6 — the matrix outvoted measured win rates ~4:1 and handed a 67% verdict to the comp with the *worse* win rates, contradicting the suggestion ranking on the same draft. **Keep the two code paths' verdicts consistent**: `getDraftAdvice` ranks candidates, `computeWinSplit` grades the finished draft, and they must not disagree about who is favoured. Closed 2026-08-31: duplicate-class was `×0.7` in the suggestion and a flat `−3` in the win split; both now read the same `classDiversity.duplicatePts`, cumulative in the verdict (it grades a finished comp) and marginal in the recommender (a pick is charged only the step it adds).

## Engine scale contract: every term in win-rate points

**Added 2026-08-30.** `getDraftAdvice` scores on a base that is itself a win rate (`blendMapGlobal`, ~45–60), so **every term is additive and denominated in win-rate points**. No multipliers on the running score, no flat constants larger than the largest measured term. See `scoring` in the config.

This exists because the *mixture of scales*, not any single value, was the bug. An influence audit (zero each term, measure the sd of the score change over 60 real draft states) found:

| | before | after |
|---|---|---|
| Thrower pick-slot penalty | **30%** (62% on early picks) | 12% |
| Duo synergy — measured | 26% | **28%** |
| Head-to-head — measured | 22% (**1%** on early picks) | **24%** |
| Counterability | multiplicative, unmeasured | 14% |
| Class matrix / map fit / anti-tank / mode / stack / ban relief | 23% | 22% |

The two terms that are actually *validated* are now the two largest. Before, 82% of early-pick influence came from two untested constants (`throwerPenalty −50`, `antiTankFirstPick +12`) while head-to-head contributed 1%. Constants were rescaled to parity — thrower −50 → **−14**, anti-tank +12 → **+4**, space-maker +8 → **+3**, counter-stack +9 → **+4** — which is a rescale for proportionality, **not a fit**, and still wants validation.

- **The thrower pick-slot penalty is REDUCED at slot 5, not lifted** (owner, 2026-08-30). It used to apply flat on slots 1–4 and vanish entirely at 5 — a −14 cliff in a single pick, and a large part of why throwers clustered at the top of pick-5 lists. `throwerPenalty.slotMultipliers` now runs 1/1/1/1/**0.35**/0, so slot 5 keeps −4.9 points. 0.35 is a prior, not a fit: the rule bundles two risks that expire at different times. **Protection** is fully resolved by slot 5 — in the 1-2-2-1 order blue holds slots 1/4/5, so slot 5 is blue's last pick and no frontline is coming that `waivedWithProtection` has not already seen. **Counter-draft** is not — the enemy still holds slot 6, i.e. `enemyPicksRemaining/3` = 1/3 of the risk priced at slot 1, the same shape counterability and the thin-map term use. Slot 6 stays at 0 because both risks are genuinely over there, which is what `counterLadder.throwerLastPick` pays for. Measured over 24 pick-5 states on the six mode-representative maps: throwers in the top 7 went **23 → 20**, and only unprotected comps moved at all — on Center Stage into Emz/Ash, Bolt takes first from Larry & Lawrie. The chip reads "Thrower unprotected" at reduced strength rather than "Thrower too early", which would be false at pick 5. **This deliberately breaks the slot list's old tie to `mapPriority.presenceFloor`** — that floor still lifts entirely at 5 and 6.
- **Counterability** replaced `score *= blindPickFactor` (a 0.35–1.0 multiplier reaching ~−40 points). It is now `counterabilityPts × (1 − firstPickSafety) × enemyPicksRemaining/3` — it **fades as the enemy runs out of picks** instead of firing only on an empty board and vanishing the moment they reveal one brawler. The safety values stay hand-authored; see below.
- **Ban relief** (`banRelief`) credits bans that removed an answer to the candidate, weighted by how likely the enemy was to pick it. Deductive, not fitted — there is no ban data to hold out against. It replaced `firstPickCaution.waivedIfBanned`, whose only entry claimed banning Max protects Brock; **Max vs Brock is 49.81% over 37,243 games**, so that ban was worth nothing while the rule paid ~+5 points. `firstPickCaution` is now empty.

**`firstPickSafety` cannot be derived from our data, and this is settled.** Two independent attempts both contradicted the owner's ground truth in the same direction: matchup spread put Rico 2nd-safest of 95, and meta-weighted counter risk put Rico 2nd-safest of 92 with Mortis safer than Brock. The cause is structural — `vs_brawler` only covers drafts that happened, and nobody first-picks Mortis, so the punishment he would take is never observed. Without draft order in `ranked_matches` it is unrecoverable. Treat that table as expert-curated; improve its *shape*, not its values.

**A use-rate (pick-rate) term in the score was tested and rejected.** Linear, log and sqrt shapes at six weights each all lost on 23,772 held-out decisions (−0.0007 to −0.0021, every one significant, monotone in weight), and presence used as a floor lost too (−0.0012). Popularity measures what players pick, not what wins — across six maps only 27 of 42 most-picked brawlers were above 50%. **Presence may select a pool; it must never add points.** That is exactly how `mapPriority.firstPick.orderByWinRate` uses it: at slot 1 it takes the `poolSize` most-played brawlers on the map and orders **exactly those** by the same win rate the card displays, so list and card can never disagree. At the shipped `poolSize: 7` the first-pick list is literally *"the seven most-picked here, best win rate first"* — verified to reproduce that ranking exactly on all six mode-representative maps. Exceptional performers are admitted on top of that pool: `exceptionalWinRate` 57 with a 5% presence floor, read off the SHRUNK rate so a thin sample cannot fake it. That is what puts **Nori first on Hot Potato** (62.1% over 8,671 games, only the 17th most-picked) and Bolt first on Gem Fort and Dry Season. A flat 60% cut was rejected as brittle — across six maps it admits only Nori, while dropping a 59.9% staple and letting a 200-game fluke in; 57 admits four in total, 55 admits nine and drowns the most-picked character of the list.

**A small use-rate nudge is shipped at `useRate.weight` 0.02, and the size is the point.** Eleven weights across three shapes were measured; the term never helped, and only stops *hurting* once it shrinks to a tie-breaker — linear 0.10 costs −0.0017 ± 0.0013 and 0.05 costs −0.0007 ± 0.0007 (both significant), while 0.02 costs −0.0002 ± 0.0003, indistinguishable from zero. It is worth about +0.9 points to a 45%-presence staple against +0.1 to a 5% niche pick. **Do not raise it past 0.03 without re-measuring** — harm grows monotonically. The reason it can add so little: presence already enters the score in the statistically correct way, as *confidence* rather than a bonus, because `mapWRk` shrinks toward the global rate by sample and on a fixed map games = presence × matches (on a 70k-match map a 40%-presence brawler keeps 98.6% of its map rate, a 3% one keeps 84%).

## Settled: no presence or map-sample floor on suggestions

**Tested four ways on 2026-08-30, every one of them lost. Do not re-litigate.**

| gate | held-out cost |
|---|---|
| presence floor 1% | **−0.0091** * |
| presence floor 3% | −0.0102 * |
| presence floor 15% | **−0.0230** * — 7× every gain shipped that week |
| min 50 map games | −0.0077 * |
| min 200 map games | −0.0101 * |
| graded 400 games early → 0 late | −0.0042 * |
| graded 200 → 0 | −0.0040 * |
| best of a 6×6 graded grid | −0.0028 (n.s.) |

**Rare picks are not bad picks.** The picks real Masters players actually made below 1% presence won **51.6%**; below 50 map games, **51.2%**; below 15% presence, **50.2%**. A 15% floor would ban **44.5% of all real picks** and leave 12 eligible brawlers per map.

**A floor also cannot tell the two cases apart.** On Dry Season it deletes Ash (0.56% presence, 396 games, **58.1%** on the map) alongside Amber (0.20%, 144 games, **47.2%**), and backfills with Piper 49.9% / Pierce 49.0% / Max 50.6% — strictly worse advice.

**The "punishable early, safe last" question is UNTESTABLE here — do not claim otherwise.** I first reported it as measured-and-backwards; that was wrong and the error is instructive. The strata were built by *withholding* enemy picks from the scorer (`shown: foe.slice(0, nRev)`) while the outcome came from the same completed game, so they measure how much information the model was given, **not when the pick was made**. `ranked_matches` stores no draft order, so early-vs-late cannot be separated at all. Every number in the table above is still valid — those are real picks with real outcomes — but none of them speaks to pick timing.

The mechanism itself is sound and standard: a niche pick revealed early can be answered, and the same pick made last cannot. **The engine already implements exactly that**, via `counterability × enemyPicksRemaining / 3` — the risk of being answered fades as the enemy runs out of picks. `thinMapPenaltyPts` extends the same shape to map-sample thinness. Both are **priors, not fits**: they cannot be validated without draft order, so keep them modest and never let one outgrow a measured term.

A **"Thin map read" chip** below `headlineMinMapPicks` (200) states the thinness as well as pricing it — same principle as the counter matrix, make the claim true rather than suppress the evidence.

## Engine design rule: priors vs evidence

Every hand-authored number in `draftEngine.js` (map geometry, SpenLC `mapRules`, `brawlerBias`, `brawlerCounters`, `firstPickCaution`) is a **prior standing in for evidence we don't have yet** — though as of 2026-08-31 `brawlerBias`, `brawlerCounters` and `firstPickCaution` are all EMPTY, each for a measured reason recorded in the config, and runs through `dampPrior()` — it shrinks halfway to 1.0 once the brawler has a real sample on that map (`brawlerBias` damps on the *recent* sample instead, since it encodes balance changes the 14-day recency window is already built to detect). Thin data → theory leads; thick data → statistics lead. **When adding a new pro/theory rule, damp it the same way** — an undamped multiplier will out-shout genuine win-rate edges (on the ~50-point score scale, 0.70x = −15 pts, where a 5% WR edge is only 2.5 pts — that exact multiplier turned out to be `classDiversity`, priced 20x above what it measures). Map-keyed config tables resolve case- and punctuation-insensitively via `lookupByMap`, so `Belles Rock` / `Belle's Rock` both hit.

## Engine calibration — the coefficients are measured now

`scripts/calibrate.mjs` (weekly, `.github/workflows/calibrate-engine.yml`, Mondays 04:40 UTC) scores `computeWinSplit` against real outcomes and records every run in **`engine_calibration`**. It exists because every coefficient in `draft_logic_config.json` was hand-authored and had never been checked against a single game — and when first measured (2026-08-27) the shipped values scored **worse than always saying 50/50** (logloss 0.6984 vs 0.6931), claiming 70% where teams actually won 58.8%.

- **Leakage is the whole difficulty.** The live aggregates are computed FROM the games you would test on. `refresh_calibration_slice(cutoff_days)` (service_role only) rebuilds `calib_train_*` from matches **collected before** the test window and fills `calib_test_games` from `player_matches` played **after** it — a game played after the cutoff is collected after it, so it cannot leak. Which side is "blue" is randomised by a stable hash of the match key, or the label would be trivially true.
- **AUC, not accuracy or Brier alone.** Brier and logloss punish overconfidence, so a timid model beats a sharp one without carrying more information; AUC is scale-free and measures ordering only. Fit the logistic scale separately, then compare.
- **`logisticScale` MUST be refitted whenever a scoring term is added or removed** — it encodes how wide the differential runs. 14 → 23.25 when the counter matrix came out, → 33.5 when duo synergy went in, → 35.0 with the mode-rate blend, → **31.0** after the 2026-08-31 rule audit. Shipping a stale scale is exactly how the engine came to state probabilities it could not support.
- **What the ablation found:** the class counter matrix COST ranking power in the verdict (0.5587 → 0.5622 without it) and is now weighted 0 there; the head-to-head `vs_brawler` term earns its place (−0.0138 without it) at a near-optimal 0.6; the hand-authored `synergyPairs` table moved nothing at all (0.0000) and was demoted to a FALLBACK behind measured `with_brawler` duo synergy, the single largest gain (+0.0102 held out); on 2026-08-31 the fallback table itself was measured — see the rule audit below. In `getDraftAdvice` the matrix was left at 2.2x at the time; it is now the MEASURED matrix at `classCounter.adviceWeight` 2.0, which is a unit conversion rather than a promotion (the matrix got smaller, not the term louder). See the antisymmetry section above for what that measurement found.
- **Duo synergy scores the EXCESS over the pair's solo rates, never the raw duo win rate** — raw conflates synergy with individual strength, so two strong brawlers look synergistic with no interaction and the engine double-counts strength it already scored. Measured: raw +0.0088 held out, excess +0.0102.
- **TRIO synergy was tested and is noise — do not re-run it hopefully.** Measured 2026-08-27 over 76,809 distinct trios: after subtracting what the three brawlers' solo rates and their three PAIRWISE synergies already predict, the residual z-scores had mean 0.07 and sd 1.00, with 4.4% beyond |z|>2 where chance predicts 4.6%. That is exactly a null. Held out, a trio term moved AUC +0.0009 against duo synergy's +0.0102. Headline trios like "Emz+Gray+Meg +9.7pp" are the maximum of 586 noisy estimates (z=3.6, ±2.72pp) — the same selection effect that makes any best-of-N look impressive. A comp's value is its brawlers plus its pairs; there is no measurable three-way interaction left. Only 601 trios have ≥300 games, so this will not change with more data soon.
- **The honest headline: every AUC here is 0.55–0.58.** The draft explains far less of the outcome than confident percentages imply. Treat any future claim of a large predictive gain with suspicion until it survives a hold-out.
- **The recommender's own weights were fitted and held out on 2026-08-29**, separately from the verdict's. Only one change cleared its error bar: `mapPairs.suggestWeight` 1.0 → 1.8 together with `duoSynergy.adviceWeight` 1.0 → 1.6, worth **+0.0032 AUC with a DeLong paired 95% margin of ±0.0011**. Measured individually, deleting head-to-head costs −0.0075 ± 0.0030 and deleting duo synergy −0.0030 ± 0.0012, so both were underweighted. **Use the PAIRED (DeLong) margin, never each AUC's own SE** — the two scorers see identical decisions, so the SE of the difference is ~3x smaller than the SE of either AUC, and judging by the latter buries every real effect this engine can produce. Note the recommender and the verdict keep SEPARATE weights for the same evidence (`suggestWeight`/`splitWeight`, `adviceWeight`/`weight`): the recommender's can be refitted freely, the verdict's cannot without a `logisticScale` refit. `mapPriority.blendPriorGames` is the exception — it is shared by both, which is why it stays at 400 despite validation mildly preferring 150–200 on a difference of under 0.0008.
- **The map blend shrinks toward the brawler's MODE rate, not their global rate** (2026-08-30). A record in gem grab is a better prior for a gem grab map than one pooled across heist and bounty; Bolt is 59.6% on Gem Fort against 55.1% global, so the old target dragged a well-measured reading toward modes he is barely played in. Worth **+0.0009 ± 0.0008** held out — small, only just clear of its bar, but the right sign and a like-for-like comparison. It changed the VERDICT base too, widening the differential 4.45% (sd 8.690 → 9.076 over 720 drafts), so `logisticScale` went 33.5 → **35.0** as a proportional adjustment; the weekly job's fit is authoritative over that number.
- **A caution about the decision harness, learned the hard way.** It scores ONE pick against ITS OWN team's result, so terms that differentiate the two teams (head-to-head, duo) are priced correctly, while a brawler's standalone strength largely cancels out of the outcome and reads as noise. On it, shrinking the map rate toward 50% scores **+0.0012** and deleting the win-rate base entirely scores **+0.0023** — both nonsense as advice. **The harness can compare variants of the base against each other; it cannot price the base against nothing.** An earlier config note claiming 'shrinking toward 50% cost 0.0039 AUC' did not reproduce and has been corrected.
- The job exits non-zero if logloss stops beating 50/50, the shipped scale drifts >50% from the fitted one, a calibration bucket is off by >5pp, or AUC falls under 0.52.

## The 2026-08-31 rule audit — every hand-authored rule, measured

Every rule in `draft_logic_config.json` was checked against 1.5M Masters matches. **The result held out: AUC 0.5780 → 0.5818, +0.0038 with a paired 95% CI of +0.0025..+0.0051** over 54,985 games — in the range of the largest gains this engine has recorded, and it came entirely from REMOVING and RESCALING bad terms, not adding any.

**The method: discordant pairs.** Count only matches where exactly ONE side satisfies a rule's condition. Both sides played the same game, so map and opponent are controlled for free. For conditional rules ("X helps when Y") use the 2×2 interaction, or a main effect masquerades as an interaction.

**Three method rules this audit produced. Break any of them and you get a confident wrong answer:**

1. **Fit the strength coefficient, never assume it.** Removing a strength component by plain subtraction assumes a coefficient of 1.0. Measured, it was **1.004** for the counter matrix and **0.508** for `synergyPairs` — and at 1.0 the pair table ranks SNIPER+THROWER first (+2.30) and SPACE_MAKER+TANK last (−1.45), where the fitted version puts them 4th and 13th and makes ANTI_TANK+SNIPER the worst pairing. Assuming 1.0 has now produced wrong answers twice.
2. **Check for members that satisfy BOTH sides of an interaction.** BROCK and PIPER are both wall-breakers and snipers, so "my team has a wall breaker" and "my team has a sniper" are the same fact whenever either is present. That alone inflated `wallBreakSniperSynergy` from **+1.07 to +2.97** — it was counting Brock twice.
3. **These are correlations that do NOT control for brawler strength.** Every number below is an UPPER bound on what a rule should add on top of a score that already carries each brawler's own win rate.

## Hard-won pitfalls

- **Per-patch count vs all-patch cap (fixed 2026-08-17)** — the single most expensive bug so far, because it was silent and looked like normal behaviour. `get_stored_match_count` defaults to `CURRENT_PATCH`, but `MASTERS_BASELINE` is the size of the retention **window**, which `prune_ranked_matches` caps across all patches. Both scrapers compared the two:
  - `masters.py` computed `target = MASTERS_BASELINE - stored`. With 2,094 old-patch rows sitting inside the window, `stored` was permanently ~2,094 short, so every run throttled itself to ~2k matches instead of the 50k steady state. Daily collection fell 243k → 8k across four weeks and looked exactly like spider saturation. **It was not** — do not re-diagnose this as a graph-saturation problem.
  - `diamond_mythic.py` gated on the same comparison and skipped **every run from 2026-07-20 to 2026-08-17**, i.e. from the moment windowed retention shipped. The bracket served month-old data the whole time.
  Both now pass `patch_name=None`. The failure re-arms at every patch rollover if anyone reintroduces a per-patch count here, since a fresh patch starts at 0 while old-patch rows still occupy the window.
- **`make_hash` omitted the patch until 2026-08-27** — a silent data-loss bug armed at every patch rollover. While an old patch is still open, a NEW-patch game whose comp already exists from the OLD patch hashes identically and is dropped; the surviving row keeps its old `patch_id`, so the game does not count toward the new patch either. On a measured run, 10,755 of 48,620 collected rows (22%) already existed — at a rollover that share of new-patch games would vanish, biased toward the MOST COMMON comps. Adding the patch changes every hash, so the fix is scoped: **`LEGACY_HASH_PATCHES = {"67.306", "68.250"}` keeps the old formula for patches already stored** (continuity holds, nothing is re-collected) and every patch from the next one onward is hashed with its patch appended. **When adding a new patch, do NOT add it to `LEGACY_HASH_PATCHES`** — that would re-arm the bug.
- **undici**: when passing a `ProxyAgent` from the standalone `undici` package, you MUST use `import { fetch } from "undici"` — Node's global fetch rejects it with `UND_ERR_INVALID_ARG`. Also pass proxy auth as explicit `token`, not URL userinfo.
- **React**: never define a component inside another component's render — inputs remount and lose focus every keystroke (the create-tournament bug).
- **Supabase inserts** from scrapers: batch ≤2000 rows, pause between batches; a giant single insert hits statement timeout 57014 and rolls back entirely.
- **New tables need `ANALYZE`** after bulk backfill, or the planner picks catastrophic nested-loop plans.
- **Locale**: the user's browser is Hungarian — use `toLocaleString("en-US")` for number formatting or thousands separators render as dots.
- Windows dev box: PowerShell 5.1 quirks apply; the repo uses CRLF locally (LF warnings on commit are normal).
